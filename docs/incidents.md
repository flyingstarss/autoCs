# 事故复盘：三份可直接用于面试讲述的「事故 → 根因 → 修复」素材

> 本文件只记录**真实发生过、有代码改动与验证证据**的三起事故。
> 每份按面试可讲的结构整理：一句话结论 → 现象 → 定位过程 → 根因（分层）→ 修复 → 验证数据 → 可讲的取舍。
> 讲述时建议控制在 2~3 分钟：先给结论，再给定位方法，最后给取舍——不要从头讲实现细节。

---

## 事故一：预算账本被架空 —— `max_tokens=8000` 形同虚设

### 一句话结论

> 系统里有三重预算（调用数 / token / 墙钟），但 token 只在**一个**处理单元里记账，
> 其余三处模型调用全部漏记，导致 73% 的真实消耗在账本上看不见，`max_tokens` 上限根本没生效。
> 修复方式是**把记账收口到唯一模型调用入口**，让"忘记记账"在结构上不可能发生。

### 现象

这起事故没有用户可见的症状——回复一切正常，只有成本和上限悄悄失真。
它是在做架构审计时被翻出来的：审计清单里有一项"预算是否真的能拦住调用"。

系统设计意图是：

- `BudgetGuard` 持有一本账（`BudgetInfo(max_agent_calls / max_tokens / deadline_ms)`）；
- 每个处理单元调模型前预检 `remaining_tokens`，调用后按 usage 记账；
- 超限就降级或转人工。

实测用 `/chat` 跑一轮「我有哪些订单」，从 trace 事件流里能直接看到四个模型调用：

| 单元 | 动作 | token |
|---|---|---|
| P1 | 意图识别 | 554 |
| P2 | 槽位抽取 | 167 |
| P3 | 情绪与风险分级 | 262 |
| D3 | 响应生成 | 361 |
| **合计** | | **1344** |

而当时账本 `budget.tokens` 只累计了 **361**（只有 D3 那一笔）。
也就是说 **983 token（73.1%）是账外的**，`max_tokens=8000` 实际要到 2 万多才可能触顶。

### 定位过程

1. 发现对不上的第一现场：响应体里的 `budget` 快照有数（不是 0），看起来"在记账"，
   所以没人怀疑；真正暴露问题的是把 trace 事件里的 `tok=` 逐条加起来和账本比对。
2. `grep consume_tokens` 全仓只命中一处 —— `agents/decision.py`（D3）。
3. 追为什么其余三处没记：每个 `Unit.handle()` 自己调 `llm`、自己决定要不要记账，
   P1/P2/P3 都是"只想拿结果"，没人记得还要记账。
4. 关键判断：这不是"漏了一行代码"，而是**记账职责放错了层**。
   只要记账是每个单元的自选动作，新增第 5 个 LLM 单元时必然再漏一次。

### 根因（三层）

| 层 | 问题 |
|---|---|
| 代码层 | 模型调用入口分散在 4 个 `handle()` 里，记账只在其中 1 个 |
| 设计层 | 预检依赖"累计已用量"，欠账 → `remaining_tokens` 虚高 → 上限失效 |
| 观测层 | 漏记是**静默**的：不报错、不告警，只有把事件流逐条求和才看得出来 |

### 修复

**收口到唯一入口** `AgentRuntime.call_llm()`（`src/cs_agent_system/agents/base.py`，约 44–110 行），
在这一个函数里固定做三件事：

1. 调用前预检：`remaining_tokens <= 0` 直接抛 `BudgetExceeded`，不浪费一次请求；
2. 调用成功后按网关返回的真实 usage 记账 `consume_tokens(used)`；
3. 记一条 trace 事件（含耗时与 token），让"这次调用花了多少"可观测。

配套约束：**全项目只允许通过 `call_llm` 调模型**。
预检策略上刻意不按经验值预留余量——真实消耗要等响应回来才知道，
凭猜测预留会误伤本该放行的调用，把可用预算白白浪费掉。

### 验证

- 修复后同一轮：`budget.tokens = 1344`，事件流 `554 + 167 + 262 + 361 = 1344`，**完全对账**。
- 预算耗尽时不再多打一次请求：`call_llm` 预检抛错 → D3 走 `except` 回退事实骨架（有事实总比没回复强）。
- 冒烟 `_smoke.py`：**22 / 22 PASSED**。

### 面试可讲的取舍

- **为什么不用装饰器 / 中间件？** 装饰器能统一记账，但绕不过"有人直接拿 `self.llm` 调用"；
  收口到运行时方法 + 代码评审约束，才让绕过变成显式的坏味道。
- **为什么不预扣 token？** 预扣数只能是猜的；猜大了误伤，猜小了仍超。宁可"事后记准 + 耗尽即拦"。
- **这起事故的价值**：它证明"有预算代码"不等于"预算生效"，可观测性缺失会让失效静默存在。

## 事故二：槽位跨轮污染 —— 用户换了对象，系统还记着上一个

### 一句话结论

> 用户说"我有哪些订单"却只回一单，说"那个订单"却回了清单，说"最新的那一单啊"又被反问一次。
> 三个看起来无关的症状，根因是同一条：**槽位没有"来源"信息，旧值被三条写入路径反复固化**，
> 系统无法判断"这个订单号是不是已经不适用于当前问题"。

### 现象（用户原话）

| 用户输入 | 期望 | 实际（修复前） |
|---|---|---|
| 我有哪些订单 | 列出一批订单 | 只回最近一单 |
| 查一下我的订单呢 | 列出一批订单 | 仍然只回一单（同一天被用户追问「怎么还是这个问题」） |
| 我想看看那个订单 | 反问"您说的是哪一单？" | 直接返回清单 / 最近一单 |
| 最新的那一单啊 | 定位到最新一单 | 二次反问"您说的是哪一单"，形成死循环 |

共同特征：**上一轮的 `order_no` 一直活着**，本轮无论问什么，工具都拿它去查同一个订单。

### 定位过程

1. 用 trace 对齐每轮的输入/输出：P2 输出的 `slots` 在用户已经换话题后仍然带着旧 `order_no`。
2. 写复现脚本逐轮打印 `session.slots`、P2 `raw_slots`、任务栈 `pending_tasks`，
   发现旧单号在三个位置同时被"补回来"，删掉一处马上被另一处恢复。
3. 结论：不是单点 bug，而是**三条独立的写入路径都缺少失效语义**。

### 根因（三条叠加路径 + 一个设计缺口）

1. **P2 抽取回退旧值**：抽取 prompt 里给了 `known_slots`，模型看到会话里有 `order_no`
   常常原样抄回来；合并时又用"旧值 or 新值"回退，于是"抽取"退化成"回显"。
2. **`apply_delta` 只增不减**：会话态合并用 `slots.update(...)`，被判定作废的槽位
   永远删不掉，下一轮又恢复出来。
3. **任务栈回填绕过失效判定**：`setdefault` 把未完成任务的槽位直接塞回底座，
   刚判失效的 `order_no` 从后门又进来了。
4. **设计缺口（真正的根因）**：槽位只存"值"，没有"来源"——
   不知道这个 `order_no` 是哪一轮、为哪个意图填的，就没有任何依据判断它该不该继续生效。

### 修复

**核心：给槽位加来源元数据 `slot_meta`，让失效判定有依据。**

- `slot_meta = {槽位名: {"turn": 轮次, "intent": 意图}}`，由编排器在每轮写回
  （`src/cs_agent_system/orchestrator/graph.py`，约 113–126 行；失效的 key 同步 `pop`）。
- 四类失效规则（`src/cs_agent_system/agents/perception.py`，约 525–569 行）：
  1. 本轮要的是**集合**（"我有哪些订单""没发货的"）→ 旧单号作废；
  2. 本轮**明确报了新单号** → 旧值作废（用户说的最算数）；
  3. **意图切换** → 该意图来源的槽位作废；
  4. 本轮表达了**状态筛选**（"已取消的""在途的"）→ 旧单号作废。
  另外，同意图但来源轮次相隔 ≥ 2 轮，也判为旧值。
- 失效槽位必须**同时从本轮抽取结果里剔除**，否则模型又把旧单号抄回来，判定等于白做；
  唯一例外是本轮用户亲口报的新单号（`perception.py`，约 575–600 行）。
- 任务栈回填同样要过失效判定，避免从后门恢复（同上，约 590–598 行）。
- 会话态写入改为 **slots 整体快照覆盖**，不做合并（`src/cs_agent_system/core/state.py`，约 37–64 行）。
- 配套：识别指代表达（"那个订单/这一单/该订单"）→ 无单号时走澄清；
  "最新/最近/最后一单" + 含"单"字 → 直接定位最新一单，避免二次反问。

### 验证（修复后实测，同一会话连续三轮）

| 用户输入 | 实际结果 | 路由 |
|---|---|---|
| 我有哪些订单 | 「您名下共有 4 单：SO202610290733 已取消，189.0 元；SO202610280001 退款中…」 | `direct_tool` |
| 我想看看那个订单 | 「您说的是哪一单？麻烦把订单号发给我，我马上帮您查。」 | `clarify` |
| 最新的那一单啊 | 「您的订单 SO202610290733 当前状态是「已取消」，实付 189.0 元。」 | `direct_tool` |

对应 trace：`tr_5851e4ca7cd1448e` → `tr_4f76893b3fa247f2` → `tr_d5c05571f4cb4595`。
冒烟 `_smoke.py`：**22 / 22 PASSED**。

### 面试可讲的取舍

- **为什么不"每轮清空槽位"？** 最省事，但同意图多轮补槽位（"黑色""M 码"）会全丢，
  用户被迫重新说一遍；正确做法是"**保留但可失效**"，失效依据必须是可解释的规则。
- **为什么不用模型判断"这个订单号还有效吗"？** 模型判断不可回归、不可解释，
  排障时无法回答"为什么这轮它被丢了"。规则化后每轮 trace 里的 `stale_slots` 就是证据。
- **判定不了的旧槽位保守保留**：宁可多问一句，也不能凭空丢掉用户已确认的订单号——
  这是准确性与啰嗦度之间的明确取舍。

## 事故三：合规改写把事实改成病句 —— 「100% 精梳棉」→「大概率精梳棉」

### 一句话结论

> 客服回答商品材质时，把事实「100% 精梳棉」输出成「大概率精梳棉」。
> 第一反应是"模型幻觉"，但用 mock 模型路径复现后依然出现，才定位到真正的元凶：
> **合规层的违禁词替换表把「100%」当成了绝对化宣传，机械替换成「大概率」**。
> 修复分三层：词表纠偏 + 事实校验反向检查 + 生成层数字回填，防复发。

### 现象

用户问卫衣材质，回复里写的是「大概率精梳棉」——

- 事实错误：商品参数是 `材质: 100% 精梳棉`；
- 语句不通：变成病句；
- 更麻烦的是：Q2 事实校验当时**判过了**，因为输出里一个数字都没有，正向比对"无可比对"。

### 定位过程

1. 初步假设：模型把数字"润色"掉了（LLM 常见行为）→ 先怀疑 D3。
2. 用 mock 模型（不调真实 LLM、直接返回骨架）跑同一问 → **依然出现「大概率」**，
   说明提交给模型的骨架已经是错的，问题在生成之前或模型之外。
3. 在 D3 出口与 Q3 出口各打一条日志做二分：
   - D3 产出：`100% 精梳棉`
   - Q3 之后：`大概率精梳棉`
4. 定位到 `src/cs_agent_system/guardrails/compliance.py` 的 `_sanitize()`：
   `ABSOLUTE_WORDS` 里有 `"100%" / "百分百"`，替换表里对应 `"大概率"`。

### 根因（三层）

| 层 | 问题 |
|---|---|
| 规则层 | 广告法语境下的"绝对化用语"词表，误伤了**成分含量**这类事实描述 |
| 处理层 | `_sanitize()` 做**无条件字符串替换**，不区分"宣传用语"与"参数事实" |
| 校验层 | Q2 只做正向校验："输出里的数字必须在事实里找得到"；<br>查不出反向情况："**事实里的精确值在输出里消失了**"——一个数字都不剩，正向看完全干净 |

### 修复（三层，任何一层单独都不够）

1. **词表纠偏**（`guardrails/compliance.py`，约 19–26 行与 84–104 行）：
   从 `ABSOLUTE_WORDS` 与 `_sanitize` 替换表中移除 `"100%" / "百分百"`，
   并写明理由：成分含量属事实描述，含量准确性交给事实校验，不靠合规改写。
2. **Q2 反向校验**（`guardrails/factcheck.py`，约 93–105 行）：
   事实里出现的百分比，必须在输出中原样出现，否则记入 `unsupported`
   （理由："缺失检测"比"多余检测"更重要——精确值被抹掉时正向校验是瞎的）。
3. **D3 数字回填兜底**（`agents/decision.py`，约 25–35 行与 445–450 行）：
   模型输出若丢了骨架里的百分比，**整段退回服务端填充的事实骨架**（骨架里的数字一定对），
   同时把本轮置信度降为 `PARTIAL`——不静默假装是模型原稿。

### 验证

修复后同一问题实测：

> 亲，这款纯棉圆领卫衣是 **100% 精梳棉**，克重 320g，版型宽松，适合春秋穿，售价 189.0 元。

- `100%` 保留、`大概率` 不再出现；
- 冒烟 `_smoke.py`：**22 / 22 PASSED**；
- 若未来模型再次丢数字，第 2、3 层会各自兜住：Q2 判不过 → D3 回填骨架。

### 面试可讲的取舍

- **为什么不是"在 prompt 里让模型别改数字"？** 指令约束不可靠、不可回归；
  保障层必须有确定性兜底，模型只负责表达，不负责保真。
- **为什么反向校验比正向校验更关键？** 正向查"编造"，反向查"丢失"。
  这起事故里输出没有任何数字，正向校验天然放行——**校验的方向决定了它能发现哪类错误**。
- **为什么保留了改写能力？** 合规改写本身没错（"绝对""最好"仍要降级），
  错的是把事实性参数塞进宣传词表。修复是**缩小规则边界**，不是关掉保障层。

## 附：支撑以上三起复盘的可观测性改造

三起事故的定位都依赖同一个能力：**事后能按 `trace_id` 完整复盘一轮对话**。
此前每轮的事件流只存在内存里、随响应返回，进程一重启就没了，排障只能重跑脚本。

本次改造：

- `traces` 表落库（`src/cs_agent_system/registry/db.py`）：每轮一行，含输入、意图/置信度、路由、目标单元、
  是否转人工、降级原因、质量分、是否自助解决、token、最终回复、完整事件流；
- 数据面 `src/cs_agent_system/registry/traces.py`：`put / get / list_recent / summary`，
  DB 不可用时退化为内存环形缓冲（最近 200 轮），**可观测性失败不拖垮业务**；
- 三个接口（`src/cs_agent_system/api/__init__.py`，约 360–378 行）：

| 接口 | 回答的问题 |
|---|---|
| `GET /trace/{trace_id}` | 这一轮到底发生了什么？（含 18 条事件流、耗时、token） |
| `GET /traces?limit=&session_id=` | 最近几轮都走了什么路径？ |
| `GET /metrics?limit=` | 系统整体在变好还是变差？（转人工率、澄清率、降级率、空回复率、平均/P95 延迟、平均 token、意图分布） |

验证记录：

- `POST /chat`「我有哪些订单」→ `trace_id = tr_5851e4ca7cd1448e`，
  `/trace/{id}` 返回 `intent=ORDER_STATUS, confidence=0.95, route=direct_tool, targets=[E1], tokens=1344, events=18`；
- `/traces?limit=5` 返回 5 轮；`/metrics` 正确聚合：
  `turns=5, avg_tokens=1320.0, avg_latency_ms=3640.9, p95_latency_ms=4251.0, clarify_rate=0.2,
  intent_distribution={ORDER_STATUS:3, PRODUCT_QA:1, CHITCHAT:1}`；
- 不存在的 `trace_id` 返回 `404` + 中文提示。

**排障时按"三问"用**：这一轮怎么了 → `/trace/{id}`；最近发生了什么 → `/traces`；要不要报警 → `/metrics`。
